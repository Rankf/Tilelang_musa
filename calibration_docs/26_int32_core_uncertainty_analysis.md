# 26. INT32 核心数不确定性分析与方案记录

状态：draft（待上传校准文档目录）
日期：2026-08-08
对象：MTT S5000（PH100 芯片，PingHu 架构），MUSA 4.3.5

## 一、问题定义

`int32_cores_per_sm` 参数存在唯一确定性缺口：

- 当前取值 `64`（照搬 NVIDIA H100 的估计值），但**未从 S5000 实测或厂商资料确认**。
- DeepStack 模型用公式 `int32_cuda_core_flops = sm_count × 频率 × int32_cores_per_sm × 2` 预测 INT32 性能。
- 按 `64` 计算理论峰值为 **11.52 TOP/s**，而实际实测仅 **4.35 TOP/s**，模型会**高估约 2.6 倍**。

## 二、实测数据（P8 专用探针）

### 2.1 INT32 MAD（x*3+1），4 路独立流

| 测量项 | 值 |
|:-------|:---|
| 实测吞吐 | 4.35 TOP/s |
| 每 SM 每 cycle 线程级操作 | 48.3 ops/cycle/SM |
| 每 SM 每 cycle warp 指令 | 1.51（若 MAD=1 指令）|

### 2.2 INT32 ADD（x+=1），数据依赖，多 ILP

| ILP | 吞吐 | 说明 |
|:---:|:----:|:-----|
| 4 | 3.45 TOP/s | 含 `d=(i&1)?1:2` 开销 |
| 8 | 4.65 TOP/s | |
| 16 | 5.62 TOP/s | 最优（含开销）|

### 2.3 通过模型公式反推的核心数范围

| 假设 | 反推核心数 |
|:-----|:----------:|
| MAD=2 ops，用 4.35 TOP/s | 24 |
| MAD=1 op，用 4.35 TOP/s | 48 |
| 纯 ADD 最优，用 5.62 TOP/s | 31 |
| **范围** | **24 ~ 48** |

范围跨度大，无法据此确定唯一核心数。

## 三、根因分析

实测 INT32 吞吐远低于 FP32，**不能简单归因于核心数少**，而是指令级效率问题：

### 3.1 关键观察：`x*3+1` 可能不是单条 IMAD

`mcc -resource-usage` 显示 `int32_mad`（x*3+1）比 `fp32_fma`（fmaf）**多用 1 个 Temp 寄存器**，说明 `x*3` 需要额外计算（可能被编译为移位+加法，而非单条 IMAD）。

### 3.2 指令吞吐反推

| 假设 `x*3+1` 编译指令数 | INT32 指令吞吐 | 占峰值(4)=比例 |
|:------------------------:|:-------------:|:--------------:|
| 1（IMAD） | 1.51 inst/cycle/SM | 37.8% |
| 2（IMUL+IADD） | 3.02 inst/cycle/SM | 75.5% |
| 3（SHL+ADD+ADD） | 4.53 inst/cycle/SM | 113%（不可能）|

若编译成 **2 条指令**，INT32 指令吞吐为 **3.02 inst/cycle/SM**，占峰值 75.5%，属仪器正常水平。

### 3.3 结论

- INT32 实测偏低主要源于**指令级效率**（`x*3+1` 非单指令、模型 `×2` 假设不匹配），而非核心数。
- 模型公式 `×2` 假设每核心每周期 2 个操作，INT32 实际达不到。

## 四、厂商资料检索结果

| 检索来源 | 结果 |
|:---------|:-----|
| MUSA 头文件（mma.h、device_functions.h、mp_ext_*_intrinsics.h） | 仅功能声明，无硬件单元数 |
| mcc `-resource-usage` | 给出寄存器/共享内存用量，不披露核心数 |
| calibration_docs 既有文档 | 无 INT32 单元数信息 |
| TileOPs 源码 | 无 INT32 单元数信息 |
| S5000 公开微架构文档 | PH100（PingHu）无公开 microarchitecture 文档 |

**结论：无法从公开资料确认真实 INT32 单元数量。**

## 五、方案对比

### 方案一：改模型代码，增加 INT32 独立利用率天花板（推荐）

给 INT32 增加独立的 `int32_max_util` 校准系数，将理论峰值压回实测水平：

```
int32 有效峰值 = 11.52 × int32_max_util = 4.35 TOP/s
int32_max_util = 4.35 / 11.52 = 0.378
```

- **优点**：不改核心数，直接校准模型预测，与实测匹配。
- **缺点**：需修改模型 cost 代码（.so 为编译产物，改源码需重新编译）。
- **核心数保留**：`int32_cores_per_sm` 保持 64（NVIDIA 类似设计，合理）。

### 方案二：从厂商/文档确认真实核心数

- 需 S5000 微架构白皮书或 MUSA 内部资料。
- 若确认核心数为 24（假设 MAD=2ops），直接改 `int32_cores_per_sm = 24`。
- 当前无此资料，暂不可行。

### 方案三：暂不处理

- 若分析以 GEMM（Tensor Core）、FP32、访存类算子为主，INT32 误差基本不影响结果。
- 仅 INT32 类算子（量化推理、整数 kernel）预测会偏乐观。

## 六、建议

1. **短期**：`int32_cores_per_sm` 保持 64，文档标注"未实测"。
2. **推荐方案一**：给模型增加 `int32_max_util` 系数（≈0.378），使 INT32 预测匹配实测。
3. **长期**：申请 S5000 微架构资料，确认真实 INT32 单元数。
