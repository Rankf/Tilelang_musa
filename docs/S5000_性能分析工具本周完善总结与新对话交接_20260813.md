## 3. “Tile维度”的准确含义

技术方案中的“Tile维度”不是只指TileOPs算子库里的一个完整算子，而是更细的kernel内部Tile操作和代表性Tile pipeline。

层级关系如下：

```text
TileOPs完整算子（例如GemmOp、FlashAttention）
  └─ 一个或多个kernel
      └─ 一个或多个代表性Tile pipeline
          ├─ T.copy
          ├─ T.gemm
          ├─ T.reduce
          ├─ T.atomic
          └─ store/copy等Tile action
```

不同指标中的Tile维度侧重点：

- 编译期metadata：Tile操作类别、读写范围、buffer层级、依赖、pipeline和stage。
- 性能建模：每类Tile action的计算或搬运代价，以及代表性Tile pipeline。
- 缓存预测：A/B/KV等tensor Tile块的访问次序、复用距离和层级流量。
- 运行期采集：Tile pipeline或Tile实例在CTA、SM、cluster等执行单元上的实测行为。

4096³ GEMM已经被拆分为以下Tile操作：

```text
fill C fragment = op_00482a5309f05771
copy A          = op_a4e41ee4df136690
copy B          = op_aa8718a84345e162
gemm            = op_1543d5dc0c6f297c
copy C          = op_f2bd1297b0eb62ec
```

因此当前不只是输出GEMM整体耗时，还能把计算关键路径定位到具体`T.gemm`，把A/B搬运关联到具体`T.copy`。

## 8. 5.7跨层级搬运异常检测

### 8.1 原问题

原先没有直接的结构化异常字段，需要人工读取多个流量和代价字段判断。

### 8.2 新增字段

```json
"transfer_anomaly_analysis": {
  "summary": {
    "anomaly_count": 0,
    "warning_count": 2,
    "normal_count": 5
  },
  "findings": []
}
```

### 8.3 自动检测规则

| 检测问题 | 判断方式 |
|---|---|
| L1下游流量异常 | L1下游流量是否超过可进入L1的逻辑流量 |
| 跨层流量守恒 | `L2输入 ≈ L1下游流量 + TMA bypass流量` |
| DDR读取放大 | DDR读取是否超过L2输入 |
| 重复搬运放大 | 逻辑读取量÷最小必要读取量 |
| 层级搬运压力 | 该层service cost÷kernel延迟 |
| 低效路径 | 找出出现放大或压力过高的L1/L2/DDR/Shared路径 |

每条finding输出规则ID、路径、状态、严重度、观测值、参考值、阈值和原因。

### 8.4 通用性边界

检测器基于统一的`memory_hierarchy_prediction`字段，不硬编码4096³字节数。同一规则已经接入GEMM、ReLU和Add。

准确表述：

> 已形成基于统一内存层级Schema的可复用规则检测框架，目前覆盖GEMM、ReLU和Add模型路径，并在S5000 GEMM上完成验证。

不能扩大为已经验证任意算子和任意硬件。

### 12.4 MCU口径注意事项

默认Memory Workload Analysis给出的：

```text
L2 Cache Hit Rate ≈ 92.32%
```

而自定义原始指标：

```text
l2pu__sector_hit_rate.pct ≈ 35.5%
```

两者不是同一统计定义，不能混用。当前与模型对比采用默认section中的L2 Cache Hit Rate，并在结果中保留口径说明。

Compute和Shared也不能直接与模型百分比相减：

- 模型compute利用率是有效FP16 GEMM计算资源利用率；
- MCU默认Compute(MP)是MP聚合口径；
- MCU的TC计数器是TC-FP32命名/语义；
- 模型Shared利用率是总字节服务利用率；
- MCU Shared指标是分离的LSU load/store管线占用。

## 13. 模型与真实采集对比

| 指标 | 性能分析工具预测 | 真实采集 | 差值/误差 | 可比性 |
|---|---:|---:|---:|---|
| Kernel延迟 | 995.90 μs | 1027.15 μs（60次Event平均） | -31.25 μs，-3.04% | 直接可比 |
| 有效吞吐 | 138.00 TFLOPS | 133.81 TFLOPS | +4.19 TFLOPS，+3.13% | 直接可比 |
| L2利用率/吞吐率 | 30.60% | 30.36%（3次MCU平均） | +0.24个百分点，+0.79% | 基本可比 |
| DDR利用率/吞吐率 | 9.70% | 6.62%（3次MCU平均） | +3.08个百分点，+46.60% | 需继续统一流量和峰值分母 |
| L2命中率 | 92.80% | 92.32%（3次MCU平均） | +0.48个百分点，+0.52% | 基本可比 |

主要结论：

1. 延迟和吞吐误差约3%，当前模型对该GEMM整体预测较接近实测。
2. L2利用率和默认口径L2命中率与MCU非常接近。
3. DDR相对偏差较大，需要继续核对模型流量、MCU物理流量及峰值带宽分母。
4. Compute、Shared和waves的模型/MCU字段定义不同，不能直接作为预测误差。

## 14. 编译前后线程配置差异

本周发现：

```text
pre-lowering metadata：128 threads / 4 warps
后端生成kernel/MCU：  256 threads / 8 warps
```

这不是普通预测误差，而是编译前请求配置与后端实际launch配置不一致。

当前正式模型使用pre-lowering metadata，因此尚未消费实际后端线程配置。后续需要利用post-lowering分析或后端编译信息补充实际launch配置，并与高层TileOp metadata合并。

不能因此否定5.1的metadata提取能力，但它是后续提高模型输入真实性的重要方向。

## 17. 5.9和5.10的数据需求判断

### 17.1 5.9计算-IO重叠

模型可以输出：

- compute代价；
- memory代价；
- 理想重叠时间；
- 理论关键路径。

但“实际重叠程度”必须有运行期计算与搬运时间区间、async copy事件、wait/barrier或类似trace。仅有kernel总耗时和聚合利用率不足以计算实际overlap rate。

### 17.2 5.10负载不均

不需要新实测就能补的模型侧能力：

- 理论CTA到SM/cluster分配；
- 每个scale unit预计Tile数；
- tail wave理论空闲率；
- 理论代价分布和方差；
- 模型侧负载不均判断。

需要真实运行数据的能力：

- 每个CTA实际执行时间；
- 每个SM/cluster实际工作量；
- active/idle周期；
- 动态shape、稀疏或MoE导致的真实长尾。

因此5.10当前部分缺口可以先由模型补齐，完整实测验证依赖5.4采集。
