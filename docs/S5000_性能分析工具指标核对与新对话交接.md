## 1. 当前工作的目标

本轮工作不是重新编写一套性能公式，而是在S5000硬件Profile和TileSight既有模型基础上，补齐以下关键链路：

1. 从TileLang PrimFunc/TIR提取5.1要求的Tile元数据和pipeline结构。
2. 建立稳定的`kernel_id`、`pipeline_id`、`op_id`索引。
3. 让性能分析工具真正读取这些metadata，而不是继续要求用户手工重复输入GEMM shape、tile、warp和stage。
4. 将TileSight模型结果回填到真实TileOp ID和pipeline ID。
5. 把底层已有的逐操作数缓存数据、跨层搬运数据和模型代价输出到正式报告。
6. 明确区分模型预测与运行期实测，不能把模型时间线写成trace，也不能把未接入的采集器算作工具能力。
7. 删除会绕开metadata校验的旧人工GEMM接口和一次性诊断脚本。

## 2. 当前正式工作流

### 2.1 已经打通的仅建模链路

```text
TileLang PrimFunc / IRModule
        │
        │ export_tile_metadata.py显式调用
        ▼
analyze_prim_func() / analyze_tir_after_vectorize()
        │
        ▼
tilesight/tile-metadata-v1
        │
        │ analyze_gemm_from_metadata()
        ▼
metadata结构校验与GEMM模型输入自动推导
        │
        ▼
TileSight calculate_matmul_pipeline_wave()
        │
        ▼
代价、缓存、搬运、瓶颈和层级报告
        │
        ▼
按kernel_id / pipeline_id / op_id回填
```

这一链路已经是实际代码调用关系，不再是“人工读取metadata后再手工传参”。

### 2.2 仍需准确理解的“自动”边界

当前已经自动完成：

- metadata到GEMM模型输入的结构识别、校验和推导；
- 模型调用；
- 结果到真实ID的关联和报告输出。

当前尚未自动完成：

- TileLang每次正常编译时自动触发metadata导出；目前通过`export_tile_metadata.py`显式执行；
- 运行kernel并读取硬件计数器；
- 将实测事件回填到相同op_id；
- 模型预测与实测数据的自动交叉校准。

因此当前正式能力属于“编译期metadata驱动的仅建模模式”，不是运行期采集闭环。

## 3. 5.1 Tile元数据实现

### 3.1 正式入口

代码位置：

- `DeepStack-ae-source/src/tilesight/tilesight/tir_interface/analyze_tir/core.py`
- `DeepStack-ae-source/src/tilesight/tilesight/tir_interface/analyze_tir/pre_lowering.py`
- `DeepStack-ae-source/src/tilesight/tilesight/tir_interface/analyze_tir/after_vectorize.py`

公开函数：

```python
analyze_prim_func(prim_func, device)
analyze_tir_after_vectorize(mod, device)
```

原先为空实现的`analyze_tir_after_vectorize()`现在会调用统一TIR分析核心：

```python
return analyze_tir(mod, device, phase="after_vectorize")
```

如果lowering后仍保留TileOp语义，分析器会保留这些信息；如果TileOp已经被降成普通TIR，则只输出能从lowered TIR保守确认的事实，并在`diagnostics`中标记语义损失，不猜测原始TileOp。

### 3.2 metadata Schema

当前Schema：

```text
tilesight/tile-metadata-v1
```

顶层主要字段：

- `architecture`
- `analysis_phase`
- `kernels`
- `summary`
- `value_kind=compiler_observed_and_semantically_derived_metadata`

每个kernel主要包含：

- kernel名称和`kernel_id`；
- grid、thread binding、线程数；
- global/shared/local buffer、shape和dtype；
- loop及编译注解；
- TileOp类别、读写区域和硬件层级；
- operation依赖关系和DAG；
- pipeline、stage count和`pipeline_id`；
- coverage和diagnostics。

ID由编译期结构生成，能够在同一metadata产物内作为模型和报告的统一索引。

### 3.3 已验证的4096³ GEMM metadata

示例产物：

```text
docs/tilesight_5_1_gemm_4096_output.json
```

已提取：

```text
kernel_id   = kernel_a0316b506d1f69cc
pipeline_id = pipeline_55cb7cd195173372

fill C fragment = op_00482a5309f05771
copy A          = op_a4e41ee4df136690
copy B          = op_aa8718a84345e162
gemm            = op_1543d5dc0c6f297c
copy C          = op_f2bd1297b0eb62ec
```

编译观察到：

```text

Block Tile     = 128 × 128 × 64
threads/block  = 128
warps/block    = 4
pipeline stage = 2
grid tiles     = 32 × 32 = 1024
```

### 3.4 5.1当前限制

- 当前示例使用pre-lowering PrimFunc导出，因为此阶段TileOp语义最完整。
- after-vectorize入口已经实现，但lowering可能已经消除TileOp语义。
- pipeline的总体`stage_count`可以读取；若编译器没有给每个操作显式stage注解，则`stage_assignment_status`为`unavailable_without_explicit_per_operation_annotation`。
- 当前ID能统一同一份metadata内的建模与报告，但尚未验证在不同lowering阶段自动保持同一个op_id。
- 运行期采集尚未消费此索引，所以“建模、采集、报告和调试全部采用同一索引”还未形成完整证据。

结论：5.1的核心metadata提取和模型/报告索引已经实现；若按指标中“供建模、采集、报告和调试统一使用”的完整承诺审核，仍缺采集接入和跨阶段ID保持验证。

## 4. metadata如何驱动性能模型

### 4.1 正式Python接口

```python
from analyze_op import analyze_gemm_from_metadata

report = analyze_gemm_from_metadata(
    "docs/tilesight_5_1_gemm_4096_output.json"
)
```

### 4.2 自动推导内容

`derive_gemm_model_input()`通过编译器观察到的数据流结构识别：

```text
global A ─copy→ shared A ┐
                         ├─gemm→ local C ─copy→ global C
global B ─copy→ shared B ┘
```

然后推导：

- `M/N/K`：来自global A/B/C buffer shape及一致性校验；
- `bm/bn/bk`：来自GEMM TileOp的`tile_shape`；
- `nw`：`threads_per_block / 32`；
- `ns`：来自pipeline编译注解；
- A/B/C操作角色及对应真实`op_id`；
- S5000 FP16 global→shared→local→global内存路径。

输入不完整、结构歧义、shape不一致、线程数非法或dtype不是当前支持的FP16 A/B/C时直接报错，不使用默认值补齐。

### 4.3 结果回填

模型完成后，`_attach_metadata_index()`会：

- 给报告添加`kernel_id`和`pipeline_id`；
- 给A/B Tile缓存和搬运明细添加copy op_id；
- 给关键路径添加GEMM op_id；
- 输出`tile_op_model_mapping`，说明模型角色与编译期操作的对应关系。

当前关键路径已经能定位到：

```text
op_1543d5dc0c6f297c / gemm / compute
```

不再只输出笼统的`gemm`或`copy`类别。

## 5. 5.2 Tile性能建模

当前GEMM模型通过TileSight的`calculate_matmul_pipeline_wave()`计算：

- compute代价；
- DDR、L2、Shared搬运量及服务代价；
- prologue、steady、epilogue；
- pipeline iteration的计算/访存代价；
- wave和occupancy影响；
- 关键路径和瓶颈类型；
- kernel级预测延迟与吞吐。

所有模型结果使用：

```text
value_kind=model_estimate
```

当前缺口：

- barrier/wait/sync没有独立代价模型；
- 当前metadata自动建模路径严格支持已验证的FP16 GEMM结构，不是任意TileOp的通用自动派发器；
- 没有实测代价与模型代价的自动对照。

因此5.2对当前FP16 GEMM仅建模范围已有完整可查询结果，但不能扩大表述成任意算子、同步代价及实测校准均已完成。

## 6. 5.3缓存行为预测

本轮没有重写TileSight的L2命中率算法，而是把底层已经计算的逐操作数数据保留下来并正式输出。

GEMM现可输出A/B各自的：

- tile shape；
- 每K迭代请求字节；
- 总逻辑请求字节；
- L2请求、命中、未命中字节；
- L2预测命中率；
- 预测DDR读取字节；
- Shared写入字节；
- 对应copy op_id和pipeline_id。

层级语义：

```text
TMA/异步global→shared：普通L1 = bypass / not_applicable
L2：使用TileSight复用距离模型预测
DDR：根据L2 miss推导读取量
Shared：报告搬运和访问量，不伪造“Shared命中率”
```

普通Elementwise路径另有简单的L1容量/复用和cold/warm L2条件预测。

当前限制：

- GEMM已有按A/B copy op_id的Tile明细，但还不是任意TileOp/任意缓存层级的通用访问模式分析器；
- 缓存结果是预测，不是硬件计数器实测；
- Shared Memory不是Cache，命中率明确为`not_applicable`。

## 7. 5.5离线分析与报告

`analyze_op.py`支持三种输出：

```text
json          完整模型JSON
hierarchical  tilesight/hierarchical-report-v1
summary       终端可读摘要
```

层级报告包括：

- kernel摘要；
- 资源利用率热点排序；
- TileOp类别热点；
- A/B Tile搬运热点；
- 模型pipeline时间线；
- ordinary L1、L2、DDR、Shared层级视图；
- kernel/SM/thread block/warp scale unit；
- 缓存行为；
- 跨层搬运异常汇总；
- 关键路径真实op_id。

`analyze_session.py`可以把多个已有模型JSON聚合成：

```text
tilesight/session-report-v1
```

并输出kernel热点、串行模型时间线和session汇总。

必须保留的语义边界：

- 层级报告只是对已有模型字段的展示转换，不修改计算公式；
- pipeline时间线是模型时间线，不是运行期trace；
- session当前按输入顺序串行聚合，不推断并发或kernel间实测间隔。

## 8. 5.6、5.7、5.8当前状态

### 8.1 5.6 Tile pipeline瓶颈

已有：

- compute与memory iteration代价比较；
- DDR/L2/Shared各层服务代价；
- `compute`、`ddr`、`l2`、`shared_memory`瓶颈分类；
- 关键路径定位到真实GEMM op_id；
- memory路径成员可关联A/B copy op_id。

未有：

- 独立sync/barrier/wait代价及同步瓶颈判断；
- 模型与实测对照；
- 任意算子的通用关键路径回填。

### 8.2 5.7跨层级搬运异常

`transfer_anomaly_analysis`会自动执行结构化规则：

- ordinary L1下游流量检查；
- L1/TMA→L2流量守恒；
- L2→DDR放大；
- 逻辑搬运放大；
- L1/L2/DDR/Shared service pressure。

输出`normal`、`warning`、`anomaly`或`not_applicable`，并带阈值、观测值、严重度和说明。

4096³当前自动结果：

```text
anomaly_count = 0
warning_count = 2
normal_count  = 5
```

其中会警告逻辑Tile搬运放大和L2服务压力。这是基于模型的自动发现，不是实测异常检测。

### 8.3 5.8缓存利用异常

已有用于分析的预测数据：

- A/B各自L2命中率；
- 命中/未命中/DDR字节；
- 层级流量；
- service pressure；
- 跨层搬运异常规则。

尚未实现完整5.8闭环：

- 没有运行期缓存计数器输入；
- 没有预测与实测命中率/流量的自动对照；
- 没有独立、通用的`cache_anomaly_analysis`对低命中率、操作间流量不均和预测偏差进行统一判定；
- 尚不能据此校准cost model。

因此5.8目前是“预测数据和部分模型侧规则可用”，不能判为完整解决。
