# S5000 性能分析工具 — 使用说明

## 一、概述

本工具基于 **DeepStack** 性能分析引擎，为 **MTT S5000（PH100 芯片，PingHu 架构）** GPU 提供算子级性能建模与预测能力。通过 **18 个硬件参数（9 必要 + 9 重要）** 的完整校准（P0~P8），实现对 S5000 上各类算子的延迟、带宽、利用率、缓存命中率等指标的准确预测。

### 核心能力

- **Tile 级性能建模**：基于 tile pipeline 和目标硬件配置，估算计算/访存/搬运代价
- **缓存行为预测**：预测 L1/L2/DDR 的缓存命中率与搬运量
- **Pipeline 瓶颈分析**：定位计算/带宽/同步瓶颈，输出利用率指标
- **Wave 效应分析**：考虑 CTA 调度波次对延迟的影响
- **三种工作模式**：仅建模、仅采集、交叉校准

## 三、快速开始

### 3.1 环境要求

- **Python**: 3.10
- **MUSA SDK**: 4.3.5（当前）/ 5.2.0（已安装）
- **PyTorch**: 2.7.1a0
- **torch_musa**: 2.7.1
- **TileLang-MUSA**: 本地编译版本

### 3.2 运行 GEMM 分析

```bash
cd /root/s5000-calibration

# 终端摘要：模型输入全部来自5.1编译期metadata
python3 analyze_op.py \
  --tile-metadata docs/tilesight_5_1_gemm_4096_output.json \
  --report-type summary

# 5.5结构化层级JSON（只改变报告视图，不改变模型计算）
python3 analyze_op.py \
  --tile-metadata docs/tilesight_5_1_gemm_4096_output.json \
  --report-type hierarchical \
  -o /root/s5000-calibration/results/reports/gemm_4096_hierarchical.json
```

`--report-type`支持：

- `json`：默认值，完整原始性能分析JSON；
- `hierarchical`：5.5层级报告JSON；
- `summary`：适合终端查看的热点、时间线、层级和Scale Unit摘要。

### 3.2.1 从5.1 Tile元数据自动运行模型

性能工具可直接读取`tilesight/tile-metadata-v1`产物，无需重复手工输入
M/N/K、Tile、warp、stage和内存路径：

先从TileLang PrimFunc生成5.1 metadata（只做编译期IR分析，不运行Kernel）：

```bash
/root/s5000-calibration/.venv-tilelang-musa/bin/python \
  export_tile_metadata.py \
  --factory workloads.gemm_4096_tilelang:make_prim_func \
  -o docs/tilesight_5_1_gemm_4096_output.json
```

`--factory`也可以指向用户自己的Python模块，只要目标函数返回TileLang
`PrimFunc`或`IRModule`。

```bash
python3 analyze_op.py \
  --tile-metadata docs/tilesight_5_1_gemm_4096_output.json \
  --report-type summary
```

工具从全局Buffer shape、GEMM TileOp、pipeline annotation和
`threads_per_block`推导模型输入，并将性能结果回填到编译器生成的
`kernel_id`、`pipeline_id`和具体`op_id`。当前自动路径严格支持已验证的
FP16 GEMM；元数据缺失或结构歧义时直接报错，不使用猜测值。人工GEMM参数
CLI已经删除。

结构化输出：

```bash
python3 analyze_op.py \
  --tile-metadata docs/tilesight_5_1_gemm_4096_output.json \
  --report-type hierarchical \
  -o docs/gemm_4096_metadata_hierarchical.json
```

多个Kernel JSON可进一步生成Session级报告：

```bash
python3 analyze_session.py \
  results/reports/gemm_1024.json \
  results/reports/gemm_4096.json \
  --session-id gemm_session --report-type summary
```

当前报告中的热点和时间线均明确标记为`model_estimate`。Session输入顺序按
串行聚合；它不是运行期实测trace。接入5.4采集产物后才能输出实测TileOp和
Session时间线。

### 3.3 运行 Elementwise 分析

```bash
# Relu
python3 analyze_op.py relu --N 16777216

# Add
python3 analyze_op.py add --N 16777216
```

### 3.4 调优输入

```bash
# GEMM的shape、tile、warp和pipeline stage应在TileLang workload/调度中修改，
# 然后重新导出metadata并运行分析，不在分析CLI中重复输入。

# Elementwise 调优参数
python3 analyze_op.py relu --N 16777216 --threads 256
```

### 4.2 指标解读

| 指标 | 含义 | 高值含义 | 低值含义 |
|:-----|:-----|:---------|:---------|
| `latency_us` | 预测执行延迟 | 性能差 | 性能好 |
| `compute_throughput_tflops` | GEMM 有效计算吞吐（TFLOP/s） | 计算吞吐高 | 计算吞吐低 |
| `effective_bandwidth_gb_s` | Elementwise 逻辑读写量除以预测延迟（GB/s） | 有效带宽高 | 有效带宽低 |
| `ddr_util_pct` | DDR 带宽利用率 | 访存瓶颈 | 非访存瓶颈 |
| `compute_util_pct` | 计算单元利用率 | 计算瓶颈 | 非计算瓶颈 |
| `l2_util_pct` | L2 缓存利用率 | L2 压力大 | L2 空闲 |
| `smem_util_pct` | 共享内存利用率 | SMEM 压力大 | SMEM 空闲 |
| `l2_hit_rate_pct` | L2 缓存命中率 | 缓存友好 | 缓存不友好 |
| `tiles_per_sm` | 每 SM CTA 数 | 并行度高 | 并行度低 |
| `waves` | 调度波次 | 负载均衡差 | 负载均衡好 |

### 4.3 瓶颈判断

```
compute_util 高 + ddr_util 低  → 计算瓶颈
compute_util 低 + ddr_util 高  → 访存瓶颈
compute_util 高 + ddr_util 高  → 混合瓶颈
l2_hit_rate 低                 → 缓存不友好，可优化访问模式
tiles_per_sm 低                → occupancy 不足，需调整资源使用
waves 高                       → 尾波效应明显，可增大工作负载
```

### 5.3 L1 Cache / Shared 补充校准

| 参数或行为 | 当前值 | 证据口径 |
|:-----------|:------:|:---------|
| 普通 cached-load L1 有效容量 | **32 KiB/MP** | working-set 与并发 CTA 扫描实测 |
| L1 cache line | **64 B 候选** | stride/coalescing 扫描实测候选 |
| L1 sector | **32 B 候选** | stride/coalescing 扫描实测候选 |
| L1 Cache 物理峰值 | **7168 GB/s** | MCU `l1__cache_bandwidth.avg` |
| L1 Cache 当前有效吞吐 | **约 5.2–5.6 TB/s** | 16 KiB/CTA、2 CTA/MP、ILP4 cached-load |
| TMA Global→Shared | **旁路普通 L1** | GEMM 4096³：TME 约 328 MB，普通 L1 下游约 21 KiB |
| Shared 命中率 | **not_applicable** | Shared 是显式寻址存储，输出流量、占用和代价 |

预测模型按访问路径拆分：普通 Global Load 进入 L1；TMA/异步
Global→Shared 作为 L1 bypass 直接进入 L2/TME；Shared 只计算搬运量、
读写量和代价。Elementwise 的冷启动/预热状态由
`--cache-condition cold|warm` 显式输入。

补充六组 GEMM scaling 测试表明，模型的 `logical_tma_bytes` 与 MCU
`l2pu__tme_read_l2_byte.avg` 不能用全局固定系数换算：固定
128×128×64 Tile 时条件除数约为 6.62，但 2048³ 的 64×128×64 与
128×64×64 Tile 分别约为 9.31 和 12.27。报告因此同时保留“逻辑 Tile
搬运量”和“MCU TME avg 硬件观测”，不直接计算跨口径 APE。

对于能驻留 L2 的 warm Elementwise 工作集，命中率不再输出精确 100%。
P9 ReLU/Add 1M 实测字节派生命中率为 99.73%/99.81%，模型使用校准值
99.75%，并同时输出 `calibrated_prediction_range_pct: [99.0, 100.0]`。
Elementwise 顶层 `l2_hit_rate_pct/l2_util_pct/ddr_util_pct/smem_util_pct`
也已从同一分层模型回填，避免旧字段与新字段给出两种答案。

### 5.7 跨层级搬运异常输出

报告新增 `transfer_anomaly_analysis`，每条规则包含：

```text
rule_id / path / status / severity
observed / expected / threshold / reason / value_kind
```

当前自动检查：L1 下游读放大、L1/TMA→L2 流量守恒、DDR 读放大、
相对最小有效数据量的逻辑搬运放大，以及各层传输 service pressure。
状态区分 `normal/warning/anomaly/not_applicable`。该输出仅依赖算子
shape、Tile pipeline 和 S5000 Profile，不要求也不接收 MCU/MSYS 数据。
硬件采集只用于离线校准和验证，不属于性能分析工具的运行输入。

## 七、S5000 实测 vs 预测对比

### GEMM 4096×4096×4096（FP16，128×128×64 tile，stage2）

MCU 显示实际 kernel 为 256 threads，即 8 warp，因此硬件验收使用
`--nw 8`；源码请求的 `--nw 4` 仍可作为模型输入，但不能冒充本次实际 launch。

| 指标 | MSYS 实测（S5000） | DeepStack（8 warp、实际内存层级） | 误差 |
|:-----|:-----------------:|:--------------:|:----:|
| 延迟 | 1034.277 µs | 994.941 µs | -3.80% |
| 算力 | 132.884 TFLOP/s | 138.138 TFLOP/s | +3.95% |
| L2 峰值带宽利用率 | 29.58%（MCU） | 30.58% | +1.00 百分点 |

### 验证结论

- **GEMM 大 shape（4096³）**：按 MCU 实际 8 warp launch 和实际内存层级，延迟误差 3.80%
- **GEMM 小 shape（1024³）**：误差较大（22~26%），因 prologue 模型未校准，需进一步优化
- **elementwise**：模型预测延迟，但未计算 DDR/计算利用率（模型功能缺口）

## 十、常见问题

### Q1: 如何验证 GEMM 预测是否准确？

```bash
# 1. 用编译期metadata驱动TileSight预测
python3 analyze_op.py \
  --tile-metadata docs/tilesight_5_1_gemm_4096_output.json

# 2. 用 TileLang 实际在 S5000 上运行
cd /root/s5000-calibration
/root/s5000-calibration/.venv-tilelang-musa/bin/python \
  benchmarks/bench_gemm_4096.py
```

### Q2: 如何修改硬件参数？

编辑 `s5000.py` 中的 `make_s5000_config()` 函数，或直接修改 `StackedGpuConfig` 参数值。

### Q3: 如何切换 MUSA 5.2.0？

```bash
# 5.2.0 已安装到独立目录，不覆盖 4.3.5
# 需要通过 LD_LIBRARY_PATH 指定
LD_LIBRARY_PATH=/usr/local/musa-5.2.0/latest/lib \
  /usr/local/musa-5.2.0/latest/bin/musaInfo
```

### Q4: GEMM 吞吐和 Elementwise 带宽的单位是什么？

- GEMM 使用 `compute_throughput_tflops`，单位是 **TFLOP/s**，计算公式为 `2*M*N*K / latency / 1e12`。
- Relu/Add 使用 `effective_bandwidth_gb_s`，单位是 **GB/s**，计算公式为逻辑读写字节数除以预测延迟。
- `flop_count` 和 `logical_traffic_bytes` 分别给出上述派生指标的计算基数。
